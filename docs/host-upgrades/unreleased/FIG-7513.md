# FIG-7513: Collect unreachable cycles before reporting terminal memory

| Old contract | New contract / host action | Commit and ticket | Missed-change diagnostic or symptom |
| --- | --- | --- | --- |
| At the end of an uninterrupted run, `Meters.memory` could include unreachable cycles that an earlier memory-pressure sweep would have freed. The same completed program could therefore report different held bytes under two memory bounds. | The terminal arena cleanup also collects unreachable cycles. Terminal memory figures can decrease; no opt-in or store reset is required. For the recorded Python reproducer, successful uninterrupted execution reports 36,432 bytes at both the 43,520-byte bound and the 64 MiB bound, instead of 36,544 and 37,440 respectively. | This commit, FIG-7513 | Identical completed guest state reports different memory solely because one run previously encountered memory pressure. |

A construction bailout now resumes at the first unpaid charge region, including
adjacent split heads. Previously a reference layout could skip one expression
charge before a later memory refusal. The recorded 38,912-byte Python case now
refuses at charge 579 in both layouts, rather than 579 and 578. This restores a
missing expression charge; operation formulas and the canonical charge schedule
are unchanged.
No opt-in or store reset is required.

This is a partial repair. FIG-7513 remains open: reference helper temporaries,
cold frame and value accounting, saved capacity floors, and the complete
refusal/restore law still prevent executor- and checkpoint-independent memory
bounds.
