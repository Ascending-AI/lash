# FIG-7650: Migration reports carry validated lifecycle states

Hosts that consume `lash::postgres::MigrationStep` must match its variants:
`Planned { migration, plan }`, `RunningBackfill`, `AppliedExpand`,
`AppliedBackfill` and `AppliedContract`. The former flat fields `phase`,
`migration`, `release`, `state`, `from_version`, `to_version`, `started_at_ms`,
`finished_at_ms`, `backfill_cursor` and `backfill_rows` are replaced by each
variant's required data. `migration()`, `phase()` and `is_applied()` expose the
common identity, typed phase and completion fact. Plans use `MigrationPlan`;
backfill variants carry `BackfillProgress` with `cursor()` and `rows()`.
Applied timestamps are required, and backfill and contract carry one unchanged
component `version`. These types are also exported by `lash_postgres_store`.
The `lash::postgres` exports use the existing `postgres` feature. No new
feature or configuration opt-in is required. `lashctl migrate` keeps its
existing JSON field names and values.

Hosts that retain PostgreSQL stores from the previous component generation
must drain and recreate the Lash trust domain using this build's `schema.sql`
or `lashctl migrate --phase expand`. The new schema rejects running expand or
contract receipts, applied receipts without finish times, running receipts
with finish times, and backfill or contract receipts that change component
version. The ledger decoder reports `StoreError::StoredDataCorrupt` for an
invalid receipt, including during reruns and contract admission. There is no
old-generation reader or migration path. The landing-generated table below
records the allocated component stamp.
