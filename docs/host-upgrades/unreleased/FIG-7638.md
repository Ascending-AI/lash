# FIG-7638: Error objects across host and guest boundaries

| Old contract | New contract / host action | Commit and ticket | Missed-change diagnostic or symptom |
| --- | --- | --- | --- |
| Host failures could carry arbitrary `ErrorDatum.data` without guest object properties. Guest TypeScript errors and Python exceptions used separate payload conventions. | All error producers use the shared object construction rule. Every newly created error has enumerable own `code` and `message`. Tool failures retain the provider code; read-provider failures use `read_failed`; other errors default to their kind. TypeScript keys and JSON include those fields. `error.data` in guest code retains the original failure, including typed tool `raw` data or Python exception arguments and causes. Guest-defined custom properties and their visibility remain intact. No opt-in is required. | This commit, FIG-7638 | Missing `error.code`, empty error JSON, or inaccessible Python host-failure details indicate an old pin. |
| Hosts could construct `ErrorDatum` literals or read and replace its public `data` field. Native errors could allocate any payload. Serialized errors admitted payloads without properties. | Construct boundary errors with `ErrorDatum::new(kind, message, raw)`. Use `raw()` for original failure evidence and `data()` for the complete object representation. Native error allocation requires the `ErrorObjectValue` returned by `error_object::native`. Error decoding rejects representations without a properties map and retained raw data. Recreate retained stores and opaque values with the new format stamps before deploying this cutover; no old-shape decoder is provided. | This commit, FIG-7638 | Private-field or native payload type errors identify callers requiring migration. Old serialized errors fail validation. |
