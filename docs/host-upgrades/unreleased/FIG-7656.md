# FIG-7656: json.classify takes no depth and JSON.stringify of deep data stays native

| Old contract | New contract / host action | Commit and ticket | Missed-change diagnostic or symptom |
| --- | --- | --- | --- |
| Kernel native `json.classify(value, depth, excluded, key_from, key_until, integers)`, native version 1: the caller passed a depth in 1..64, out-of-range depths raised `number_range`, and a cycle was unrolled to that depth. | `json.classify(value, excluded, key_from, key_until, integers)`, native version 2: the depth bound is the configured document depth (`KernelDataLimits::document_depth`), and a container on its own active path is refused. Version 1 keeps its exact implementation for archived definitions. Helper release 0009 records the change. Kernel documents that call `json.classify` drop the depth argument. | This commit, FIG-7656 | A document passing six arguments to version 2 fails arity validation. |
| `JSON.stringify` of plain data nested more than eight containers deep (ordinary JSON schemas) took the generic prepare/copy walk, costing seconds of cell CPU per few kilobytes. | Plain data up to the document depth takes the native render, at a constant charge per input byte. No host action. | This commit, FIG-7656 | A cell stringifying nested tool schemas hit `CELL_BOUND_EXCEEDED`. |
