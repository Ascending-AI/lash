# FIG-7665: Diagnostic messages cannot be blank

| Old contract | New contract / host action | Commit and ticket | Missed-change diagnostic or symptom |
| --- | --- | --- | --- |
| Shared `Diagnostic::message`, TypeScript `Diagnostic::message`, and `workflow::ModuleError::message` were `String`; shared `Diagnostic::new` and `Diagnostic::dialect` accepted arbitrary strings. | Messages are `lash::dialect::DiagnosticMessage`. Shared constructors require that type. Use `DiagnosticMessage::authored(text)` for producer-owned prose, `TryFrom<String>` for fallible validation, `as_str()` to borrow, or `String::from(message)` to consume. No new feature or policy opt-in is required. | This commit, FIG-7665 | Raw strings passed to shared constructors or assigned to message fields fail to compile. Blank producer-owned prose panics at construction. |
| Serialized diagnostics accepted an empty or whitespace-only `message` string. | The wire field remains a string. Decoders reject blank messages with `diagnostic message is blank`; existing non-blank messages decode unchanged. Upgrade diagnostic producers and consumers together when older producers can emit blanks. | This commit, FIG-7665 | A new consumer rejects a blank diagnostic emitted by an old producer. |
| TypeScript and Python entry signature refusals could render only `SIGNATURE_REQUIRED: ` or `ENTRY_ANNOTATION_REFUSED: `. | Messages name the entry, missing or refused annotation, parameter or result, and an accepted signature such as `run(): Promise<unknown>` or `def run() -> object:`. Shared signature facts converted without language information show both forms. Codes, reason facts, spans, and repair channels are unchanged. No opt-in is required. | This commit, FIG-7665 | Hosts that display `message` or the diagnostic's display text now receive an explanation rather than an empty suffix. |
