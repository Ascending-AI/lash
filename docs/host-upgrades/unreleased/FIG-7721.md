# FIG-7721: Only exported TypeScript functions are workflow entries

| Old contract | New contract / host action | Commit and ticket | Missed-change diagnostic or symptom |
| --- | --- | --- | --- |
| In a TypeScript workflow module, every top-level function declaration and top-level `const` bound to a function was an entry, exported or not, and had to carry an entry-grade signature. | Only a top-level function the module exports (`export function`, `export const f = ...`, or a local named in `export { f }` / `export { f as g }`) is an entry. Any other top-level function is a module-local helper: its return type may be inferred, and annotations such as `v is T`, `ReturnType<typeof pkg.op>`, `Awaited<...>` and indexed access are accepted. Sources whose entries were not exported must add `export`. No opt-in is required. | This commit, FIG-7721 | A module whose only functions lack `export` is refused with `WORKFLOW_EMPTY_MODULE`; a non-exported function no longer appears in `Document::exports` and cannot be started. |
| `lash::dialect::Diagnostic::entry_signature(refusal, language)`. | `Diagnostic::entry_signature(refusal, language, params: &[String])`, where `params` is the entry's whole parameter list as the accepted signature spells it in `language`. Entry refusal messages now keep every parameter, for example ``accepted signature, for example: `readPage(id: string): Promise<unknown>` `` instead of `` `readPage(): Promise<unknown>` ``. | This commit, FIG-7721 | Callers of `entry_signature` with two arguments fail to compile. Hosts that match message text see the parameter list in the accepted signature. |
