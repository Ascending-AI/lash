How To Use This Page

Use this as a routing table. App-facing guides say what to wire; architecture pages explain why that wiring works.

Note

If two pages mention the same concept, the task row points at the canonical home. For example, session persistence lives in Persistence; replay and effect durability live in Durability and replay.

Turn Work

Running turns is the core application path. Pick collected output for backend jobs, streaming output for interactive UI, and pending next-turn input when user follow-up should dispatch durably after the current turn.

run a turn

Build LashCore, open a LashSession, call session.turn(TurnInput::text(...)).run().await?, then read TurnOutput::assistant_message(). Start with Quickstart, then use API basics for the full facade shape.

stream a turn

Implement TurnActivitySink and call TurnBuilder::stream_to(&sink), or use pull-style stream(). For browser reconnect and service-boundary streams, use Streaming and reconnect.

persist a session

Install a SessionStoreFactory on LashCoreBuilder::store_factory(...), use file-backed attachment/artifact stores, and reopen the same session id after restart. See Persistence wiring.

delete a session

Call LashCore::delete_session(..., scope) for factory-backed sessions. A materialized host-facing id is permanently retired, so reset flows must rotate to a new id; deleting a never-materialized id is a no-op. If a process registry is installed, Lash removes that session's observer edges and wake bookkeeping and deletes its trigger subscriptions without changing process lifecycle. See Delete sessions.

Host Surface

The host decides what the model can see and do: tools, prompt contributions, projected state, and plugin-specific input.

add a tool

Use StaticToolProvider and StaticToolExecute for fixed app tools; implement raw ToolProvider only for dynamic manifests, dynamic contracts, or custom provider behavior. Install the provider through LashCoreBuilder::tools(...), plugin registration, or the session/core ToolAdmin. See the Tools guide; use Plugin basics only when the tool also needs plugin state, prompt hooks, or runtime hooks.

expose state to RLM

Use RlmProjectedBindings for read-only names in Lashlang scope. Use JSON/value bindings for small state and ProjectionRef bindings for large host objects behind a resolver. See Projected bindings and RLM variables.

Long-Running Work

Use child sessions for delegated reasoning, Lashlang processes for reusable background work, and process wakes when background events should re-enter the model through queued work.

spawn subagents

Install SubagentsPluginFactory, choose or define capabilities, and let RLM call spawn_agent. Child sessions receive constrained specs and their usage rolls up to the parent. See Subagents.

start background work

Install a ProcessRegistry with .process_registry(...) plus a SessionStoreFactory (required at build()); the default inline worker runs each process in an ephemeral runtime built from its captured execution environment, never by reopening the origin session. Pass .process_work_driver(...) when an external durable runner owns work execution. Observe and control runs through core.processes() (host-level) or session.processes() (observer-scoped). See Process work and Durability and replay.

Inspect And Debug

Use traces for runtime-level evidence and read views for committed app-facing state.

inspect traces

Attach JsonlTraceSink with .trace_sink(...), set TraceLevel, and render the JSONL with lash-trace-viewer. Add a separate Lashlang execution sink when you need foreground/process execution graphs. See Tracing.
